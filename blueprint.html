02 Screen flow

Three screens. The interesting part isn't the navigation — it's the two different ways a session reaches Ended, and what the pending screen is actually doing while it waits for the scale.

HomePending + Ended
  • Create sits top-right, always reachable, not buried in a menu.
  • Each pending row carries a connected or disconnected chip — state alone isn't enough, so it also carries time since last reading, since a scale can sit “connected” and silent.
  • Ended rows are grouped by day, newest first, each showing its per-product totals inline — no tap needed just to see the number.
SessionPending
  • Every incoming reading appends a row; the same product can appear many times, each row deletable with an Undo toast rather than a confirm dialog.
  • End session is a visible action here, not just a background job — a shift ending early shouldn't have to wait for midnight.
  • Back returns to Home without ending the session; it keeps running in the background.
SessionEnded
  • Read-only by design — it renders straight from session_product_summary, never the raw entry list, so it can't drift from what was reported at close.
  • Shows why it ended (manual or auto_eod) — useful the first time someone asks why a session closed with an odd total.

03 Key decisions

The choices worth flagging before anyone builds against this — each one trades something away on purpose.

Delete is soft, with Undo — not a confirm dialog
Confirm dialogs get reflexively tapped through by busy staff; a brief Undo window actually prevents accidental loss without slowing down repeat weighing.
The connection indicator carries a timestamp, not just a state
“Connected” can lie — a scale can hold the link while sending nothing. Showing time-since-last-reading is what actually tells staff whether it's safe to keep weighing.
Two paths to Ended, one rollup
Manual close and the midnight job must write the identical session_product_summary shape — the Ended screen has no idea, and shouldn't need to know, which one fired.
Summaries are written once, not recomputed on read
If a product gets renamed six months later, a closed day's totals shouldn't silently change. History is a record, not a live query.
Entries save locally before they save anywhere else
A shop-floor connection is the least reliable part of this whole system — a reading should never be lost because the network dropped a beat.
